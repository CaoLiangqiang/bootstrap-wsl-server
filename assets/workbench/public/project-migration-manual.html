端到端移植手册

2. 迁移前盘点

先在项目电脑形成一页迁移记录，至少回答：

  • 远程仓库、目标分支和准备发布的提交 ID 已确认。
  • 运行时及版本已确认，例如 Python、Node.js、Java、数据库或浏览器组件。
  • 启动、停止、健康检查和版本查询方式已确认。
  • 所有配置键已列出，并区分普通配置与秘密。
  • 数据库、上传文件、报告等持久数据已列出，容量和停机窗口已评估。
  • Windows 专属路径、盘符、批处理、COM、Office、驱动或硬件依赖已识别。
  • 预期主机名、访问人群、资源上限和回滚版本已与管理员确认。

发现必须依赖 Windows GUI、内核驱动或本机硬件且无 Linux 替代方案时，先停止迁移并重新设计；不要用兼容层掩盖核心依赖。

3. 传输代码与数据

首选：从权威 Git 仓库克隆

先按客户端手册连接服务器，再在 WSL 中使用项目自己的认证方式克隆。私有仓库凭据只在服务器本地配置，不从其他电脑复制凭据文件。

mkdir -p ~/codebase
cd ~/codebase
git clone <approved-repository-url> <project-name>
cd <project-name>
git switch <branch>
git rev-parse HEAD

无法直接克隆：Git bundle

在项目电脑创建 bundle，经 SSH 复制后，在 WSL 克隆。它保留提交历史，适合暂时无法访问远程仓库的情况。

# 项目电脑
git bundle create project.bundle --all
scp -P __SSH_PORT__ project.bundle __WSL_USER__@<Windows-LAN-IP>:~/

# WSL
git clone ~/project.bundle ~/codebase/<project-name>

仅传非 Git 数据

大量数据优先使用支持断点续传的 rsync；Windows 自带环境可用 scp。先传到暂存目录，核对清单和校验值，再由管理员放入正式数据目录。

scp -P __SSH_PORT__ -r <local-data-directory> \
  __WSL_USER__@<Windows-LAN-IP>:~/migration-staging/
不要把项目放在 /mnt/c 或 /mnt/e 长期运行。源代码、虚拟环境和运行数据应位于 WSL 的 Linux 文件系统；Windows 挂载盘只用于经确认的导入或导出。

4. Linux 适配

检查项处理原则
路径移除盘符和反斜杠；使用相对路径或配置化的绝对路径，并注意 Linux 大小写敏感。
脚本把必需的 .bat/.ps1 启动逻辑改为项目原生 Linux 命令；文本统一 LF。
依赖从锁文件重建，不复制 Windows 虚拟环境、node_modules 或已编译二进制。
配置提交无秘密的 .env.example；真实配置保存在仓库外、权限设为 600。
网络应用只监听 127.0.0.1 的未占用端口；不要自行创建 Windows 端口转发。
状态缓存与可重建依赖不备份；数据库、上传、报告和必要配置使用明确的持久目录。
接口提供快速、无副作用的健康接口，并能返回可核对的版本或提交 ID。

按项目既有工具安装并验证依赖，例如使用锁文件和隔离环境。不要使用全局 sudo pip install 或在生产目录手工修改依赖。

5. 在 WSL 内完成本地验证

先创建仓库外配置，再以普通用户运行。以下仅表示通用检查，实际启动命令以项目文档为准：

cd ~/codebase/<project-name>
<install-from-lockfile>
<run-tests-and-build>
<start-on-127.0.0.1-and-private-port>

curl --fail http://127.0.0.1:<app-port>/<health-path>
curl --fail http://127.0.0.1:<app-port>/<version-path>
ss -ltnp

用无痕窗口或全新浏览器配置验证登录、文件上传下载、长任务、报告生成、刷新和错误提示。此阶段端口仍不得从 LAN 访问。

6. 交给 systemd 长期运行

把下列信息交给管理员：工作目录、唯一启动命令、环境文件路径、回环端口、健康路径、停止超时、资源需求以及持久数据目录。管理员按服务器模板创建应用自有的用户服务。

systemctl --user daemon-reload
systemctl --user enable --now <application-service>.service
systemctl --user status <application-service>.service --no-pager
journalctl --user -u <application-service>.service --since today --no-pager

服务应设置工作目录、仓库外环境文件、失败自动重启和合理资源限制。不要在 systemd 单元中写秘密，也不要以 root 运行普通 WebUI。应用启动失败时应退出，由 systemd 记录并重试，而不是在应用内无限后台化。

7. 应用注册、HTTPS 网关与备份

由服务器管理员完成以下动作，项目负责人提供输入并参与验证：

  1. 将应用加入 WebUI 注册表，只登记服务名、回环地址、健康路径及秘密文件和持久数据的路径。
  2. 启用应用健康检查 timer，确认连续检查通过；健康检查不得修改业务数据。
  3. 为应用分配独立主机名。只有应用明确支持 base path 时才使用路径前缀。
  4. 在共享 Caddy 网关启用认证 HTTPS。应用端口仍保持回环监听。
  5. 仅由共享 HTTPS 入口通过 Windows Private/LocalSubnet 防火墙对 LAN 发布；不要为每个应用增加裸 HTTP 转发。
  6. 把秘密、持久数据和必要网关状态纳入加密备份；排除仓库、缓存、虚拟环境和可重建依赖。
绝不能通过网页、Git 或聊天分发 Caddy 私有 CA 密钥、Basic Auth 明文密码、应用令牌或 Restic 密码。客户端只安装经管理员核对指纹的公共 CA 证书。

8. 从真实客户端验收

在最终使用者电脑上完成，不以服务器本机测试代替：

  • 公共 CA 已按客户端说明安装，指纹与管理员提供值一致。
  • 未经认证访问返回 401，正确认证后返回 200。
  • 证书主机名匹配、浏览器无 TLS 警告，页面显示预期版本。
  • 核心业务流程、上传下载、长任务、刷新及并发场景通过。
  • 应用进程被终止后 systemd 能恢复；Windows 定时恢复任务状态正常。
  • 备份检查通过，并已恢复到临时目录核对关键文件。

9. 切换与回滚

  1. 冻结旧实例写入，记录旧、新版本提交 ID，并执行最后一次数据同步和校验。
  2. 先让少量真实用户通过 HTTPS 验收，再宣布切换；保留旧实例和直接测试入口只作为限时回滚。
  3. 观察服务日志、健康记录、资源占用和用户反馈，确认稳定后再停用旧实例。
  4. 回滚时先停止新实例写入，恢复兼容的数据快照和旧版本，再验证健康与核心流程。

回滚必须考虑数据库或数据格式兼容性。代码可回退不等于数据可回退；任何破坏性迁移都应先生成可验证快照。
